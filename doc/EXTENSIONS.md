## Why Extensions, Not Changes

The original three-worker architecture (`doc/Deliverable_2_Architecture_Updated_v4.docx`) defines:
- **Worker 1 (Al-Nassikh):** ingestion pipeline — *any structured text source*
- **Worker 2 (Agent 1):** query understanding — *extensible tool registry (§2.9)*
- **Worker 3 (Agent 2):** retrieval + synthesis — *source-agnostic, reads from Qdrant*

Every extension below plugs into one of these existing workers. None add a new worker or change the state contract.

## Extension 1 — Khaleeji/Emirati Lexicon (`⚡ EXT-1`)

**File:** `src/al_nassikh/khaleeji_lexicon.py`  
**Plugs into:** Worker 1 (normalisation) + Agent 1 tool registry (§2.9)

**What it does:**  
A curated dictionary of ~200 Khaleeji/Emirati dialect terms with their MSA equivalents and English glosses. Used in two places:
1. **Normalisation** — before embedding, dialect terms are bridged to their MSA equivalent so BM25 matches across dialect variants.
2. **New tool: `khaleeji_dialect_bridge`** — Agent 1 can explicitly call this tool when it detects a dialect term in the query and wants to expand the search.

**Why additive, not contradictory:**  
The architecture already has dialect handling in `resolve_heritage.py` (Stage 6) and `intent_router.py` (dialect patterns). This extension enriches that layer — it doesn't replace it.

## Extension 2 — Online Corpus Ingest (`⚡ EXT-2`)

**File:** `src/al_nassikh/online_ingest.py`  
**Script:** `scripts/ingest_online_corpus.py`  
**Data:** `data/online_corpus/khaleeji_poems.json`  
**Plugs into:** Worker 1 (ingestion) → same Qdrant index

**What it does:**  
Fetches and normalises Khaleeji/Nabati poems from publicly available Arabic poetry datasets (HuggingFace `arbml/arabic_poetry`, filtered for Gulf poets). These poems are treated as "already digitised" — they skip the Kraken HTR + eScriptorium step because they are already in digital text form.

The indexed chunks carry `source_type: "online_digitized"` in the Qdrant payload. The UI shows a 🌐 badge on results from this source, distinct from 📜 manuscript results.

**Why additive, not contradictory:**  
The architecture document explicitly describes Worker 1 as accepting PAGE-XML *or* any structured text. Online poems are structured text — they use the same `index.py` pipeline, the same chunk levels, and the same Qdrant store.

**What it demonstrates:**  
The retrieval system's quality is now visible at a larger scale. CRAG grading across manuscript AND online sources shows the agent making source-aware relevance judgements.

## Extension 3 — Audio Oral Tradition Corpus (`⚡ EXT-3`)

**File:** `src/al_nassikh/audio_corpus_ingest.py`  
**Script:** `scripts/ingest_audio_corpus.py`  
**Data:** `data/oral_tradition/` (transcriptions from MAAI7103 project)  
**Plugs into:** Worker 1 (ingestion) → same Qdrant index

**What it does:**  
Processes the 3,340 Khaleeji Nabati audio clips from the MAAI7103 project:
1. If transcriptions already exist → normalise and index directly.
2. If only audio files → run Whisper transcription first, then index.

Indexed chunks carry `source_type: "oral_tradition"` in payload. The UI shows a 🎙️ badge.

**Cross-modal bridge:**  
When a manuscript verse and an oral tradition recording contain the same poem, the system links them. A result can then say: *"This verse also appears in the oral tradition corpus — it was transcribed from an audio recording in the MAAI7103 dataset."*

**Why additive, not contradictory:**  
Nabati poetry is historically an *oral* tradition — manuscripts are the written form of what was primarily sung and recited. Ingesting oral tradition recordings is the most culturally authentic extension of the corpus, and it uses Worker 1's existing ingestion pipeline unchanged.

**Why this shows "wow" agentic retrieval:**  
The retrieval system now spans three source types (manuscript / online / oral tradition). The CRAG grader must evaluate cross-source relevance. The synthesiser can produce answers that cite evidence from all three.

## Extension 4 — Agent Reasoning Trace Panel (`⚡ EXT-4`)

**File:** Updated `app/streamlit_app.py` + `src/fatat_al_arab/state.py`  
**Plugs into:** UI layer only — no pipeline changes

**What it does:**  
An expandable panel in Tab A that shows, after every query, the live decision log of both agents:
- Which track the intent router selected and with what confidence
- The hypothetical verse generated by HyDE
- Per-retriever result counts and latencies
- CRAG grades for each retrieved passage (Correct / Ambiguous / Incorrect)
- The `requery_strategy` if a re-query fired
- Self-RAG faithfulness / relevance / completeness scores
- Whether a retry was triggered and what `fix_instructions` said

**Why additive, not contradictory:**  
All this data already flows through `AgentState`. This extension only *surfaces* it in the UI — it adds zero logic to the pipeline.

## Extension 5 — Audio Query Input from MAAI7103 (`⚡ EXT-5`)

Already partially implemented in `src/fatat_al_arab/audio_input.py` (Whisper transcription). Extension 5 makes this more prominent in the UI and connects it to the oral tradition corpus so users can say a verse aloud and find it in both written and oral tradition sources.
